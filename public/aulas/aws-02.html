As peças do IAM

O IAM (Identity and Access Management) é global: não pertence a uma Região. Ele responde duas perguntas: quem é você (autenticação) e o que você pode fazer (autorização). É gratuito.

PeçaO que éDetalhe de prova
UserIdentidade de uma pessoa ou app, com credenciais de longo prazoSenha para o Console; access keys para CLI/SDK
GroupColeção de users que herdam as policies do grupoGrupos não se aninham e não podem ser assumidos nem citados como Principal
RoleIdentidade sem senha, assumida temporariamenteCredenciais temporárias via STS; usada por serviços, outras contas e federação
PolicyDocumento JSON com permissõesAnexada a identidades ou a recursos
Regra de ouro: se um serviço da AWS (EC2, Lambda, ECS) precisa acessar outro serviço, a resposta é IAM Role. Access keys gravadas no código ou na instância são sempre a alternativa errada.

Policies

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject"],
    "Resource": "arn:aws:s3:::fotos-maju/*",
    "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } }
  }]
}
Identity-basedAnexada a user, group ou role. Não tem Principal: o principal é quem recebe a policy. Pode ser AWS managed, customer managed ou inline.
Resource-basedAnexada ao recurso (bucket policy, policy de fila SQS, de tópico SNS, de função Lambda, de chave KMS). Tem Principal: diz quem pode acessar, inclusive outras contas.

Quando usar cada tipo de policy gerenciada

  • AWS managed: prontas e mantidas pela AWS (ex.: ReadOnlyAccess). Rápidas, mas costumam ser amplas.
  • Customer managed: você escreve e reutiliza em várias identidades. Melhor para menor privilégio.
  • Inline: embutida em uma única identidade, morre com ela. Use só quando a relação 1:1 for obrigatória.

Como a AWS decide: lógica de avaliação

1. Deny explícito em qualquer policy: negado, fim.
2. SCP da Organization precisa permitir
3. Permissions boundary (se existir) precisa permitir
4. Precisa de pelo menos um Allow (identity ou resource policy)
5. Nada permitiu: deny implícito (o padrão)
Permissions boundaryTeto máximo de uma identidade. Não concede nada: permissão efetiva = policy ∩ boundary. Útil para deixar devs criarem roles sem escalar privilégio.
SCPTeto para a conta inteira (via AWS Organizations). Não concede, só limita. Afeta até o root das contas membro, mas não a management account.
Condition keysaws:MultiFactorAuthPresent, aws:SourceIp, aws:PrincipalOrgID, aws:RequestedRegion. Condição falsa: o statement não se aplica.
Pegadinha: um Deny explícito vence qualquer Allow, mesmo que o Allow venha de uma policy de administrador. E uma SCP sem Allow para um serviço bloqueia esse serviço até para o admin da conta.

Roles, STS e acesso entre contas

  • Trust policy (na role): quem pode assumir. Permission policy (na role): o que pode fazer depois.
  • Quem vai assumir também precisa de permissão sts:AssumeRole na própria conta.
  • Para terceiros (fornecedor que acessa sua conta), use External ID na trust policy para evitar o problema do "confused deputy".
  • Sem role: serviços com resource-based policy (S3, SQS, SNS, Lambda, KMS) aceitam acesso direto de outra conta, se a resource policy citar a conta externa e a identidade externa tiver Allow.

Federação e acesso de pessoas

CenárioSolução
Funcionários já logam no Active Directory / Okta / Entra ID e precisam entrar em várias contas AWSIAM Identity Center (antigo AWS SSO), com SAML 2.0
Usuários finais de app web ou mobile (milhões)Amazon Cognito (user pools para login; identity pools para credenciais AWS temporárias)
Pipeline de CI externo (GitHub Actions) acessando a AWSProvedor OIDC no IAM + role, sem access keys
Uma única conta com poucos admins, sem IdPUsers IAM com MFA (ou Identity Center mesmo assim)
Pegadinha: "milhares de funcionários" ou "milhões de usuários" nunca é "criar um IAM user para cada um". É federação + roles temporárias.

Boas práticas que viram alternativa certa

  • Menor privilégio; comece pequeno e use o IAM Access Analyzer para gerar policies a partir da atividade real e achar acessos externos.
  • MFA para root e usuários privilegiados.
  • Roles em vez de access keys; se precisar de keys, rotacione e use o credential report para auditar.
  • Grupos para dar permissão a pessoas, nunca policy direta em cada user.
